Flux de travail communs

1. Besoin

Un flux de travail (statuts et transitions) n'était visible que dans l'espace qui l'avait créé, à l'exception du flux par défaut. Chaque espace devait donc refaire le même flux (« Projet » : Préliminaire → APS → APD → DAO → Contrôle, par exemple).

On veut :

  • créer un flux une fois et le proposer à tous les espaces de travail ;
  • affecter simplement un flux à un type de tâche, depuis le type comme depuis le flux.

2. Principes retenus

PrincipeConséquence
Flux commun = flux sans espace (project_id NULL) Aucune colonne nouvelle : le flux par défaut était déjà sans espace. Même logique que Phase.isCommune() (DT-001).
Un flux commun se modifie depuis tout espace Statuts et transitions changent pour tous ; l'éditeur l'annonce par un bandeau.
Les statuts n'appartiennent à aucun espace Partager un flux ne duplique rien.
Un type ne reçoit qu'un flux visible dans son espace Flux de son espace ou flux commun ; contrôlé côté serveur à chaque affectation.

4. Règles

ActionRègle
Créer un flux communCase « Commun à tous les espaces de travail » : le flux est enregistré sans espace.
Rendre un flux communToujours permis.
Rattacher un flux commun à un espaceRefusé si un type d'un autre espace l'utilise, et pour le flux par défaut (WorkFlow.NOM_PAR_DEFAUT), donné aux types de tous les espaces.
Renommer (saveWorkFlow avec id)Ne change que le nom. Auparavant, le flux reçu du formulaire (sans statuts ni transitions) remplaçait le flux enregistré et vidait ses statuts.
SupprimerInchangé : refusé tant qu'un type, de n'importe quel espace, l'utilise.

5. Affectation à un type de tâche

  • Depuis le type (formulaire issutype-form2) : liste « Flux de travail », flux de l'espace puis flux communs. Laissée vide à la création, le serveur reprend le flux du premier parent, sinon le flux par défaut.
  • Depuis le flux (écran Flux de travail) : bandeau « Types utilisant ce flux » avec les types de l'espace, le nombre de types d'autres espaces, et une liste « + Affecter à un type… ». Pour retirer un type, lui choisir un autre flux : un type a toujours un flux.

Les tâches existantes gardent leur statut lors d'un changement de flux, comme avant (affectWorkFlow).

7. API GraphQL

# tasks.graphqls
type WorkFlow { … commun: Boolean … }

# workflow.graphqls
extend type Mutation {
    changerPorteeWorkFlow(workFlowId: Int!, commun: Boolean!, projectId: Int): WorkFlow
}

workFlowsByProject(projectId) renvoie maintenant les flux de l'espace puis tous les flux communs.

8. Migration des données

Aucune : pas de nouvelle colonne, aucun script db/manual/. À vérifier après mise à jour : tout flux déjà enregistré sans espace devient visible partout. Requête de contrôle :

SELECT id, name FROM work_flow WHERE project_id IS NULL;

Normalement seuls « Default workflow » (et, sur d'anciennes bases, « Default WorkFlow ») apparaissent. Un autre flux peut être rattaché à son espace depuis l'écran (« Rattacher à cet espace »).

9. Limites et évolutions

  • Pas de droit particulier sur un flux commun : tout espace peut le modifier (choix retenu). Une évolution possible : lecture seule hors administration, ou copie pour modifier.
  • Changer le flux d'un type ne recale pas le statut des tâches existantes sur le nouveau flux.
